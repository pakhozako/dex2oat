# Dex2oat-Lock v4.0 大版本更新框架

本文是 v4.0 主线规划，不是一次性提交清单。v4.0 的目标是把项目从
“持续快速迭代”推进到“长期维护、可验证发布、云端配套清晰、WebUI 与发布产物一致”的工程状态。

v4.0 必须是“看得出来的大版本”：

- 必须有用户可感知的新功能。
- 必须有明显的交互和界面变化。
- 必须有能被说明清楚的架构调整或职责重排。
- 必须有发布体系、云端、规则库或状态模型中的至少一项实质升级。
- 不能只做内部重构而没有外部可见变化。

4.0 对外宣传时应能明确说出：

- 新的 WebUI 工作台。
- 新的健康中心 / 诊断中心。
- 新的规则中心和规则解释。
- 新的配置时间线、备份与恢复。
- 新的发布与完整性体系。
- 新的云端可选能力和服务器职责边界。

## 1. 版本定位

v4.0 是架构边界和发布体系的大版本，不是单纯 WebUI 美化版。

核心目标：

- 明确本地模块、WebUI、构建系统、云端服务、服务器管理面板的职责边界。
- 统一 release ZIP、GitHub main 分支、WebUI 保护产物、完整性基线的关系。
- 把 `18080 = 1Panel 等成熟服务器面板`、`18082 = Dex2oat 发布/API` 纳入正式架构。
- 强化规则库、状态模型、完整性检查和配置保存的可恢复性。
- 保持 Magisk / KernelSU / APatch 官方兼容，不引入破坏性生命周期行为。
- 继续保持手机优先 Material Design 3 WebUI，但把体验优化建立在稳定架构上。

v3.9 定位：

- 作为当前稳定线。
- 只接受 P0/P1 回归修复、安全修复、发布元数据修正。
- 不再塞入大规模云端重构、发布结构重排或 WebUI 架构调整。

## 1.1 4.0 用户可见功能清单

以下功能是 v4.0 应该让用户明显感受到的变化。实现时仍可分阶段落地，但最终 v4.0 正式版不应缺席核心项。

必须交付：

- 新工作台：打开 WebUI 后能直接看到真实健康状态、待重启状态和主要操作入口。
- 新健康中心：完整性、冲突、待重启、应用状态和云端通信合并展示。
- 新规则中心：规则有解释、有命中依据、有回退路径。
- 新配置时间线：至少支持本地快照、最近保存记录和恢复上一版。
- 新诊断包：用户确认后导出，不包含敏感数据。
- 发布可信链：release ZIP、manifest、SHA256、云端 update 元数据可交叉验证。

可以延期到 4.x：

- 云端规则自动分发。
- 复杂统计图表。
- 多设备配置同步。
- 非必要的新主题和装饰动画。
- 任何需要改变现有配置格式且无法无损迁移的功能。

### 新工作台

目标：

- 首页不再只是状态卡片堆叠，而是“设备健康 + 配置入口 + 最近动作 + 待处理事项”的工作台。
- 用户打开 WebUI 后能一眼知道：当前是否正常、是否待重启、配置是否已应用、是否有异常。

建议功能：

- 顶部健康胶囊：显示 `已同步`、`待重启`、`需要关注`、`离线模式` 等真实状态。
- 最近动作：显示最近保存、最近生成 prop、最近应用、最近上传证据。
- 快捷操作：保存并生成、诊断、规则重匹配、安装历史、备份恢复。
- 状态摘要弹窗：点击摘要后完整展示配置来源、规则命中、最终 prop、待重启原因。

### 新健康中心

目标：

- 把“完整性、冲突、待重启、应用状态、规则匹配、云端通信”合并成一个健康中心。
- 小报错归类为正常提示，真正风险置顶。

建议功能：

- 健康评分或健康等级，但不要制造焦虑。
- 风险分组：正常、需要重启、需要关注、已阻止。
- 完整性状态：关键文件通过/异常/缺失，说明具体文件。
- 冲突状态：显示冲突来源和建议处理。
- 待重启状态：明确哪些变更需要重启生效。

### 新规则中心

目标：

- 从“选项列表”升级为“可解释规则库”。
- 用户知道为什么命中某条规则、它写了什么、风险是什么、如何回退。

建议功能：

- 规则分类：安全、谨慎、危险、自定义。
- 每条规则展示：作用、命中依据、写入 prop、默认状态、兼容性说明。
- 搜索和筛选。
- 规则命中详情弹窗。
- `everything` 升级逻辑解释：哪些 `speed/speed-profile` 可升级、为什么默认关闭部分风险项。

### 新配置时间线

目标：

- 让用户能看到配置变化历史，并能恢复。

建议功能：

- 每次保存生成一个本地快照。
- 显示保存时间、规则模式、启用项数量、最终 prop 数量。
- 支持恢复上一版配置。
- 支持导出诊断包时附带摘要，不附带敏感数据。

### 新诊断包

目标：

- 让用户反馈 bug 时更容易，开发者更容易定位。

建议功能：

- 一键生成诊断包。
- 包含：模块版本、管理器类型、Android 版本、规则摘要、状态摘要、完整性摘要、最近错误。
- 不包含：账号、序列号、完整日志、完整配置、应用列表、敏感 token。
- WebUI 中可预览诊断内容，确认后再导出或上传。

### 新云端可选能力

目标：

- 云端只作为辅助，不绑架本地。

建议功能：

- 更新检查。
- 公告/FAQ。
- 可选匿名使用统计。
- 用户手动确认的规则证据上传。
- 规则证据汇总用于下一版规则库优化。

### 新发布可信链

目标：

- 用户和维护者都能确认 release ZIP、GitHub release、云端 mirror、完整性基线一致。

建议功能：

- release manifest 可读。
- WebUI 关于页显示构建版本、规则版本、完整性状态。
- 云端 `update.json` 与 GitHub release SHA256 一致。
- release ZIP 解包清单与预期清单一致。

## 2. 4.0 不做什么

v4.0 不应该做这些事：

- 不把服务器变成设备端运行的必要条件。
- 不让云端规则静默改变用户设备配置。
- 不在 Dex2oat 云服务里自写服务器管理面板。
- 不暴露命令执行、文件管理、系统管理能力到 Dex2oat 公共 API。
- 不删除构建所需源码，只为了“看起来像 release.zip”而破坏可复现构建。
- 不为了 UI 动画牺牲 WebView 兼容性和低端设备性能。
- 不改变现有用户配置格式，除非提供迁移和回滚。

## 3. 官方兼容基线

v4.0 所有模块生命周期设计必须以官方文档为准：

- Magisk：保持官方模块目录、`module.prop`、`customize.sh`、`service.sh`、`system.prop`、`sepolicy.rule` 语义。
- KernelSU：保持模块结构和 WebUI 规则兼容，WebUI 不依赖标准浏览器独有能力。
- APatch：保持 APM 模块结构、Shell 生命周期和 WebUI 兼容。
- Material Design 3：WebUI 继续使用 Material You / Material 3 token、surface、motion、typography、shape、accessibility。

落地要求：

- Shell 继续以 POSIX / BusyBox / Android shell 兼容为底线。
- 不使用废弃 API。
- 不引入未经评估的新依赖。
- 任何新依赖都必须写入依赖评估记录：用途、体积、WebView 兼容性、回滚方式。

## 4. 总体架构边界

### 4.1 设备端模块

职责：

- 安装、升级、卸载。
- 规则匹配。
- 生成 `system.prop` 或 runtime 配置。
- 状态刷新。
- 完整性检查。
- WebUI 本地配置读写。

禁止：

- 依赖服务器可用性完成开机流程。
- 从云端静默拉取并立即应用高风险规则。
- 将完整日志、完整配置、系统属性全量上传。

### 4.2 WebUI

职责：

- 本地配置管理。
- 规则选择和摘要展示。
- 诊断导出。
- 可选云端通信开关。
- 手动确认的规则证据上传。

要求：

- 手机优先。
- Material Design 3 一致。
- 不横向溢出。
- 不出现 `null`、`undefined`、`NaN`。
- 所有保存动作必须有防重复提交、失败原因和恢复路径。

### 4.3 云端 Dex2oat API

正式端口：

```text
http://154.219.110.62:18082
```

这是发布与运维工具的直连地址。发布给 WebUI 的云端元数据必须走 HTTPS，
或仅在本机开发时使用 HTTP loopback；公网只有明文 HTTP 时，WebUI 远端 URL
应保持为空。

职责：

- release mirror。
- update metadata。
- releases index。
- rules metadata。
- optional anonymous telemetry。
- manual rule evidence collection。
- aggregate summary for planning。

禁止：

- 服务器管理。
- 命令执行。
- 任意文件管理。
- 设备端强依赖。

### 4.4 服务器管理面板

正式端口：

```text
http://154.219.110.62:18080
```

职责：

- 使用成熟开源面板，例如 1Panel。
- 管理服务器资源、服务、日志和面板自身安全。

禁止：

- Dex2oat 项目自写替代。
- 与 `18082` API 混用。
- 写入仓库任何面板密码、token、登录安全入口。

## 5. 4.0 工作流分阶段

### Phase 0：冻结 v3.9 稳定线

目标：

- 确认 v3.9 release ZIP、GitHub release、云端 API 元数据一致。
- 标记 v3.9 只做回归修复。
- 建立 v4.0 开发分支或明确本地工作分支策略。

验收：

- `node tools\validate.js` 通过。
- `node tools\build.js` 通过。
- `node tools\release.js` 通过。
- 云端 `18082` 返回 v3.9 元数据。

### Phase 1：发布结构与源码边界

目标：

- 解决“GitHub/main 内容与 release.zip 内容一致”的策略问题。
- 明确哪些文件进入 release ZIP，哪些文件只属于开发源码。
- 明确 WebUI 源码、保护产物、彩蛋资源、混淆结果、压缩资源的公开策略。

关键决策：

- `webroot-src/` 是否保留在公开分支。
- `webroot/` 是否只保留保护后的发布产物。
- 彩蛋歌词/封面等原始资源是否只在私有构建输入中存在。
- release ZIP 是否作为公开结构基准。

建议方案：

- 公开主分支保持可构建源码，但敏感彩蛋原始素材不入库。
- release ZIP 只包含模块运行所需文件和保护后的 WebUI。
- 若用户坚持 main 与 release.zip 完全同构，则建立单独发布分支/发布目录，不破坏开发源码分支。

验收：

- 解包 release ZIP 后的文件清单有脚本校验。
- 发布清单不包含 `docs/`、`webroot-src/`、原始彩蛋素材、临时文件。
- 构建链仍可从开发源码生成 release。

### Phase 2：云端端口与服务职责重排

目标：

- 固化 `18080 = 1Panel`，`18082 = Dex2oat API`。
- 清理旧 `18081` admin 逻辑。
- 清理自写服务器面板路线。
- 更新本地 `tools/version.json`、`webroot-src/data/app-meta.json`、云端部署工具和文档，
  并保持“工具可直连 18082、WebUI 只暴露 HTTPS/本机 HTTP”的安全边界。
- 记录当前服务器事实：Dex2oat cloud 已迁到 `18082`，`18080` 由 1Panel
  承载服务器管理面板，`18081` 空置，旧 admin 必须保持停止和禁用。

验收：

- `tools/version.json.cloudBaseUrl = http://154.219.110.62:18082`，供发布/运维工具使用。
- WebUI meta 仅在 `18082` 有 HTTPS 入口或本机 loopback 时暴露远端 URL；否则留空。
- `tools/deploy-cloud-release.py check` 检查 `18082`。
- `tools/cloud-ops.py status/health` 检查 `18082`。
- 文档不再把 Dex2oat 自写页面描述为服务器管理面板。
- 服务器面板部署由成熟上游项目承担。
- 旧 admin 不再随 release/API 工具恢复。

### Phase 3：Shell 生命周期与状态模型

目标：

- 清理安装、开机、手动执行、卸载的生命周期边界。
- 强化互斥锁、stale lock、异常退出恢复。
- 将状态文件写入、读取、合并、回滚统一成可审计模型。

重点：

- `customize.sh`
- `service.sh`
- `uninstall.sh`
- `core/state*.sh`
- `scripts/statectl.sh`
- WebUI 调用 Shell 的桥接边界

验收：

- 首装、升级、重启、WebUI 手动刷新不会并发破坏状态。
- 不读取 `/data/adb/dex2oat-lock-install.prop`。
- 状态文件损坏可恢复。
- 卸载清理不误删用户导出文件。

### Phase 4：规则库 4.0

目标：

- 规则库从“可用”升级到“可解释、可回滚、可扩展”。

工作项：

- 规则去重。
- 清理空选项、单选项无意义规则。
- 重新梳理安全 / 谨慎 / 危险分类。
- `speed-profile`、`speed` 等可兼容场景升级为 `everything`。
- 谨慎/危险分类可提供 `everything`，但默认关闭。
- `skip=false` 才可进入默认启用候选。
- 线程类、后台触发类、可关闭安全优化类按设备兼容性保守处理。

安全门槛：

- 规则错误不能导致设备不开机。
- 危险规则必须默认关闭。
- 每条规则需要说明来源、适用条件、失败回退。

验收：

- options/rules 校验无重复 ownership 冲突，或冲突有明确优先级说明。
- 生成 prop 有 dry-run 摘要。
- 规则证据可用于后续扩展，但不能自动改变设备配置。

### Phase 5：完整性、构建和发布体系

目标：

- 彻底消除完整性 missing 误报。
- 让发布产物、完整性基线、manifest、SHA256 和云端元数据形成闭环。

工作项：

- 完整性基线只覆盖 release ZIP 中关键运行文件。
- 构建后自动重新生成基线。
- release manifest 明确文件清单、大小、hash。
- 云端 mirror 与 GitHub release 对齐。
- 支持 release ZIP 清单对比检查。

验收：

- 首装默认不显示完整性缺失。
- 升级后不显示完整性缺失。
- 重启后不显示完整性缺失。
- 人为修改关键文件后能正确告警。

### Phase 6：WebUI 4.0

目标：

- 在不改变模块核心功能的前提下，完成手机优先 Material 3 系统级体验。

工作项：

- 统一 Material 3 token。
- 统一 surface 层级。
- 统一 card/button/dialog/snackbar/navigation/list/chip/progress/switch。
- 优化启动页到主界面的过渡。
- 优化所有保存、刷新、诊断、安装历史弹窗。
- 清理重复文案和空值显示。
- 防止横向滚动。
- 压缩和保护 WebUI 资源。
- 离线图标方案，不依赖联网字体。

验收：

- 手机窄屏无横向溢出。
- 无空图标。
- 无 `null/undefined/NaN`。
- 保存失败有具体原因。
- 动画尊重 `prefers-reduced-motion`。
- 旧 WebView 不崩溃，现代 WebView 保持完整效果。

### Phase 7：JSBridge 与 WebUI 安全

目标：

- 保持 JSBridge API 向后兼容，同时收紧安全边界。

工作项：

- 路径白名单。
- 禁止任意绝对路径写入。
- 禁止 `../` 路径穿越。
- 命令参数白名单。
- 输入长度限制。
- JSON schema 校验。
- 保存防重复提交。
- 配置写入锁和原子替换。
- 备份和恢复。

验收：

- 无任意文件写入。
- 无命令注入。
- 无 XSS/HTML 注入。
- 异常 Promise 不导致白屏。

### Phase 8：云端隐私与证据系统

目标：

- 让云端数据真正服务规则库扩展，同时保持用户可控和隐私最小化。

允许：

- 匿名安装哈希。
- 模块版本。
- Android 版本。
- 品牌 / 机型聚合。
- Root 管理器类型。
- 规则版本。
- 用户手动确认后的 allowlist 规则证据。

禁止：

- IMEI、Android ID、序列号。
- 账号、手机号。
- 应用列表。
- 完整日志。
- 完整配置。
- 任意文件内容。
- secret/token/password/cookie。

验收：

- 服务端二次过滤敏感字段。
- WebUI 明确用户确认。
- 上传失败不影响本地功能。
- 证据汇总只显示聚合结果。

## 6. 4.0 发布门禁

每个 4.0 RC 必须通过：

```powershell
node tools\validate.js
node tools\build.js
node tools\release.js
python tools\deploy-cloud-release.py check
python tools\cloud-ops.py status
python tools\cloud-ops.py health
```

还必须完成：

- 解包 release ZIP 清单检查。
- WebUI 手机视口检查。
- 首装真机检查。
- 升级真机检查。
- 重启后状态检查。
- Manager 是否有 warning 检查。
- 完整性人为篡改检查。
- 云端不可用时本地功能检查。

验收矩阵：

| 范围 | 必须验证 | 失败处理 |
| --- | --- | --- |
| Shell 生命周期 | 首装、升级、开机、手动刷新、卸载 | 阻止 RC，修复后重新跑全链路 |
| 状态模型 | 状态文件损坏恢复、待重启标记、冲突归类 | 阻止 RC，必须给出恢复路径 |
| 规则库 | schema 校验、重复 prop 归属、everything 升级边界 | 阻止 RC，危险规则默认关闭 |
| WebUI | 手机窄屏、横竖屏、无横向溢出、无 null/undefined | 阻止 RC，修复布局或文案 |
| JSBridge | 路径白名单、命令参数白名单、保存防重入 | 阻止 RC，做专项安全复查 |
| 完整性 | 首装/升级/重启无默认误报，人为篡改可告警 | 阻止发布，重新生成并验证基线 |
| 云端 | 18082 health/update/releases/rules 可读，18080 不承载 Dex2oat API | 不影响本地功能；云端问题阻止云端发布 |
| 隐私 | 遥测可关闭，证据手动确认，服务端二次过滤 | 阻止云端功能上线 |

## 7. 4.0 分支和发布策略

建议：

- `main`：稳定发布线。
- `develop/v4.0` 或 `codex/v4-framework`：v4.0 集成线。
- `release/v4.0-rc`：RC 验证线。
- `hotfix/v3.9.x`：v3.9 紧急修复线。

发布顺序：

1. v3.9 最终稳定快照。
2. v4.0-alpha：内部结构和云端端口对齐。
3. v4.0-beta：WebUI 和规则库进入完整测试。
4. v4.0-rc1：功能冻结，只修 bug。
5. v4.0：正式发布。

## 8. 回滚策略

每个阶段都必须可回滚：

- release ZIP 回滚到上一版。
- 云端 `update.json` 回滚到上一版。
- 规则库 schema 回滚。
- WebUI 配置备份恢复。
- 状态文件损坏恢复。
- 服务器面板与 Dex2oat API 分离，互不阻塞。

## 9. 4.0 成熟度目标

4.0 发布标准：

- 架构边界清楚。
- release ZIP 与发布清单一致。
- WebUI 保护策略明确。
- 完整性检查无默认误报。
- 配置保存跨档位无丢失。
- 规则库可解释、可回滚。
- 云端只做辅助，不影响本地启动。
- 服务器管理使用成熟上游面板。
- 文档可以指导下一位维护者独立发布。
