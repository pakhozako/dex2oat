# v3.9 DevOps And v4.0 Roadmap

This document records the post-v3.9 maintenance direction. It is a working
roadmap, not a promise to change module behavior in one batch.

## Current v4.0 Release Baseline

- Version: `v4.0 / 400`
- Release ZIP: `releases/Dex2oat-Lock-v4.0-release.zip`
- Cloud mirror/API: `http://154.219.110.62:18082`
- Server panel: `http://154.219.110.62:18080/` is reserved for the mature
  upstream server panel. Do not put a Dex2oat-authored dashboard on 18080.
- Business data panel: Directus Studio may run on `18083` for feedback,
  supporters, telemetry, rule evidence and operator records. Keep public module
  traffic on `18082`.
- Server status: Dex2oat cloud has moved to `18082`; `18080` is the 1Panel
  server panel; `18083` is Directus business data when deployed; `18081` is unused, and the legacy admin service must stay
  stopped and disabled.

- Managed server directory: `/root/codex-managed/dex2oat-lock`
- Raw easter assets stay untracked; protected release assets are generated by
  `tools/build-webui.mjs`.

Before changing anything, run:

```powershell
git status --short --untracked-files=all
node tools\validate.js
npm.cmd run cloud:check
```

## v3.9 True-Device Feedback Loop

The following items require real Magisk / KernelSU / APatch devices. Local
Windows validation is not enough.

1. Fresh install: install output, initial state, integrity status and WebUI open.
2. Upgrade install: previous config preservation, state refresh and Manager status.
3. Reboot: `service.sh` boot timing, lock release, runtime prop application.
4. WebUI phone use: startup transition, top pill, secondary dialogs, scroll,
   save/generate flow, refresh, reboot menu and background/card appearance.
5. Rule evidence: manual upload only, allowlist filtering, no logs or sensitive
   identifiers.
6. Cloud communication: optional switch, no blocking of local module behavior
   when the server is unavailable.

Feedback should include:

- manager family and version
- Android version / SDK
- device model
- install mode: fresh or upgrade
- screenshots or diagnostic export when possible
- whether reboot was completed after install

## Server DevOps Scope

The server is a managed support layer, not a replacement for device-side safety.

Allowed server responsibilities:

- release mirror and update metadata
- release/API service on 18082
- server management through upstream open-source panel software
- static docs and FAQ
- optional module communication heartbeat
- manual rule-evidence collection after user confirmation
- aggregate evidence summary for rule-library planning
- health checks, backups and operation logs
- remote CI / worker experiments inside the managed directory

Forbidden server responsibilities:

- silently changing device-side rules without schema and compatibility checks
- collecting logs, installed apps, accounts, IDs, secrets or arbitrary props
- requiring server availability for boot, save, rule matching or integrity checks
- touching unrelated server services, firewall, SSH, proxy or tenant directories

Use temporary credentials only:

```powershell
$env:DEX2OAT_CLOUD_PASSWORD = "<server password>"
npm.cmd run cloud:ops -- status
npm.cmd run cloud:ops -- health
npm.cmd run cloud:ops -- logs
npm.cmd run cloud:ops -- backups

npm.cmd run cloud:ops -- worker-selfcheck
npm.cmd run panel:deploy
npm.cmd run panel:status
Remove-Item Env:\DEX2OAT_CLOUD_PASSWORD
```

Use `cloud:check` for public mirror metadata and `cloud:ops` for managed server
health. They cover different layers.

## Remote Worker

The remote worker lives under `/root/codex-managed/dex2oat-lock/worker` and is
intended for heavy or long-running maintenance tasks such as static scans,
protected WebUI inspection, browser-based UI smoke checks and release dry runs.

Rules:

- keep worker files, repos, logs and artifacts under the managed worker tree
- run heavy commands through `scripts/run-worker-task.sh` so logs are captured
  and `nice` / `ionice` are applied
- keep worker access SSH-only; never expose a public command execution endpoint
- do not let worker experiments alter the public release mirror unless the
  normal release/deploy flow is explicitly executed and verified
- do not collect or process private user data beyond the documented telemetry
  and rule-evidence boundaries

## v4.0 Direction

The v4.0 line is a major release, not a small cleanup branch. The detailed
framework lives in `docs/V4.0_MAJOR_UPDATE_FRAMEWORK.md`; keep this section as
the short operational summary.

Plan v4.0 around visible product changes and stability:

- keep Magisk / KernelSU / APatch module structure official and minimal
- continue reducing shell race conditions and state ambiguity
- keep WebUI phone-first and Material Design 3 based
- ship visible WebUI changes: workspace, health center, rule center,
  configuration timeline and diagnostics package
- make rule-library updates evidence-driven, reversible and schema-checked
- improve diagnostics so user reports are actionable without exposing secrets
- evaluate any new dependency against Android WebView compatibility and build
  protection impact before adoption
- move expensive local checks to the server only when they do not affect release
  reproducibility or user privacy

## Review Gates

Every release candidate should pass:

```powershell
node tools\validate.js
node tools\build.js
node tools\release.js
npm.cmd run cloud:check
```

For cloud changes, also run:

```powershell
npm.cmd run cloud:ops -- status
npm.cmd run cloud:ops -- health
```

Do not mark a build publishable until local ZIP, GitHub release asset and cloud
mirror all report the same version, size and SHA256.
